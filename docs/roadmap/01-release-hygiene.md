# 01 — Finish the 0.8.0 release

**Status:** broken now. **Size:** ~20 minutes.

## What is wrong

The `v0.8.0` tag points at `1256ca40`, which is also `main`. But the tree that
tag names still describes itself as 0.7.0, and its changelog still describes
0.8.0 as unreleased.

```
fpm.toml:2          version = "0.7.0"
CMakeLists.txt:6      VERSION 0.7.0
CHANGELOG.md:8      ## [Unreleased]      <- the whole 0.8.0 feature list is under this
```

There is no `## [0.8.0]` heading anywhere in `CHANGELOG.md`; the next heading
down is `## [0.7.0] – 2026-09-13` at line 128.

## Why it matters

The version string is not decoration, it is the answer to a question consumers
ask programmatically:

- `find_package(pic 0.8 REQUIRED)` fails against this tree, because
  `PROJECT_VERSION` is 0.7.0. The generated `picConfigVersion.cmake` is written
  from `${PROJECT_VERSION}` (`CMakeLists.txt:175-178`), so the installed package
  advertises 0.7.0 too.
- fpm resolves dependencies by tag but reports the manifest version, so a
  downstream `fpm.toml` pinning pic gets a mismatch between what it asked for
  and what the build says it got.
- `.VERSION` is generated by `configure_file` from `.VERSION.in`
  (`CMakeLists.txt:10-11`) and is what `docs/pages/releases/index.md`
  interpolates into the published documentation links. Those links currently
  point at the 0.7.0 docs.

None of this breaks a build. All of it makes the release untrustworthy to
anything that reads metadata rather than source.

## The fix

1. `fpm.toml:2` → `version = "0.8.0"`.
2. `CMakeLists.txt:6` → `VERSION 0.8.0`.
3. `CHANGELOG.md`: rename `## [Unreleased]` to `## [0.8.0] – <release date>` and
   open a fresh empty `## [Unreleased]` above it, matching the shape already
   used for 0.7.0.
4. Re-tag. The existing `v0.8.0` tag points at a commit that misdescribes
   itself, so either move it to the fixing commit or cut `v0.8.1` and treat
   `v0.8.0` as withdrawn.

**Moving a tag is the part that needs a decision.** Deleting and re-pushing a
tag is fine if nothing has consumed it. fairport pins pic by SHA rather than by
tag precisely so that a moved tag cannot silently change its event-log digest,
so from fairport's side either choice is safe — but check for anything else
first.

## How to know it worked

```bash
grep -n '0\.8\.0' fpm.toml CMakeLists.txt
grep -n '^## \[' CHANGELOG.md | head -3
cmake -B build && grep PROJECT_VERSION build/CMakeCache.txt
```

A consuming project should then succeed with:

```cmake
find_package(pic 0.8 REQUIRED)
```

## Note

If you take item 03 in the same release, do all of this as part of 0.8.1 and
skip the re-tag question entirely — 0.8.0 stays as it is, and 0.8.1 is the first
release whose metadata is correct.
